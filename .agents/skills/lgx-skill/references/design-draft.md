# lgx-skill

把用户的概念或需求转化为可复用的个人技能。仅通过 `/lgx-skill` 显式调用；命令后可附概念、用途或已有技能名，无参数时先澄清需求，不生成空技能。

本技能自包含，不以当前库的正文、规则、导航、日志、模板或其他技能作为运行依赖；不替代宿主与工作区约束。设计或创建技能不等于授权执行它，不自动修改全局指令、配置其他技能或启动后续流程。

## 1. 确认需求

- 明确要解决的问题、输入、预期输出、职责边界及触发方式；已有信息直接复用，只询问会影响设计的缺项。
- 确认本次是只设计方案、创建文件，还是修改已有技能；只设计时不写文件。
- 写入前确认目标范围与目录：工作区技能或个人技能。个人用途不等于个人目录，不因当前存放在某库就把该库的维护流程带入技能。
- 需要确认时使用宿主提问工具；没有该工具则提问并等待。未确认的关键取舍不擅自补齐。

## 2. 概念命名

- 名称必须为 `lgx-<概念>`。后缀通常选表达单一核心概念的简短英文；多个词用连字符连接，不用整句需求或堆叠无关职责。
- 名称仅用小写英文字母、数字和连字符，满足 `^lgx-[a-z0-9]+(-[a-z0-9]+)*$`，总长度不超过 64 个字符；目录名与 frontmatter 的 `name` 完全一致。
- 用户只给中文概念时提出对应英文名；存在实质歧义时先确认。用户给的名称缺少前缀或不合法时提出规范名称，不按非法名称落盘。
- 写入前在已确认范围内检查重名及相关已有能力。修改既有技能时保留无关内容；同名不等于同一职责，不擅自覆盖、改名或新建近义副本。

## 3. 模块化与解耦

- **单一职责**：一个技能承担一个明确目标，写清输入、输出、不做什么以及结束条件。独立目标才考虑拆成独立技能，不为“模块化”预建技能系列。
- **最小结构**：先用一个 `SKILL.md` 组织职责与步骤；仅有实际需要时增加同目录内的参考资料、模板或脚本，不预建空目录、不复制公共正文。
- **显式接口**：需要路径、数据或外部工具时明确输入与必要条件，不硬编码当前库名、本机绝对路径、固定目录树或当前会话身份。
- **自包含**：必要流程写入技能；补充资源随技能携带并使用技能内相对链接，按需加载。迁移整个技能目录后，不应依赖原库文件才能理解或执行。
- **可组合**：如确需其他技能，先明确依赖与输入输出并取得用户同意；不因同属 `lgx-` 系列而默认串行调用。库内导航和日志不得成为技能的前置或完成条件。

## 4. 生成

仅在已授权范围内落盘，优先使用宿主支持的技能目录，例如工作区 `.github\skills\<名称>\SKILL.md` 或个人 `~\.copilot\skills\<名称>\SKILL.md`；宿主不支持时说明，不写到猜测的位置。

基本 frontmatter 如下；占位内容必须替换为本次设计，不原样保留：

```yaml
---
name: lgx-<concept>
description: '<何时使用，以及完成什么单一目标>'
user-invocable: true
disable-model-invocation: true
---
```

此模板默认生成显式调用的技能；用户明确要求自动匹配时才调整触发配置，并说明影响。描述必须包含实际用途和触发情景，不把模板说明当成描述。

正文按实际职责保留必要部分：目标与边界、输入输出、步骤及失败处理、验收条件。没有内容的章节不保留；检查失败须明确反馈，不用空结果冒充成功；有副作用的步骤须明确授权范围。

## 5. 核验与交付

1. 核对位置、命名、目录与 `name` 一致、YAML 合法、描述有意义、触发配置符合需求，资源链接均可解析。
2. 检查职责是否单一、内容是否重复；删去本次设计中不必要的抽象、步骤和资源，不能靠拆文件掩盖职责混杂。
3. 按实际目标核对正常输入、缺少必要输入、越界请求及外部依赖不可用时的预期输出与停止条件。脚本使用适用的最小测试；未授权时不通过执行新技能来验证副作用。
4. 做迁移检查：除明确声明的输入、工具和经同意的依赖外，不需要原库正文、绝对路径、导航、日志或会话数据。不能满足时说明未完成，不宣称已解耦。
5. 反馈名称、核心职责、产物位置或方案、调用方式、已核验内容及未完成项。区分“文件已创建”“宿主已发现”和“调用已验证”，未实测不宣称斜杠命令已注册或运行成功。
